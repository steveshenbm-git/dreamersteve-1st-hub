# 证据、联系人与风险规则

## 证据状态

`evidence_records` 中每条关键结论必须且只能选择下列一个证据状态：

| 证据状态 | 判定条件 | 允许的表达 |
|---|---|---|
| 官方直接证据 | 来源由相关公司、法定主体、政府或责任机构直接发布，且原文直接支持结论 | 按原文范围陈述，不扩展到未声明的实施、结果或规模 |
| 多来源相互印证 | 两个或以上可识别且相对独立的来源支持同一结论 | 说明印证范围，不得将转载链误当独立来源 |
| 单一来源待验证 | 结论仅由一个可识别来源支持，且尚无相互印证 | 作为待验证线索，不得写成确定事实 |
| 合理推断 | 有明示的已知证据和可解释的推理链，但来源未直接声明结论 | 必须使用“推断”或“可能”并列出前提，不得改写为事实 |
| 来源相互冲突 | 可识别来源对同一关键事项给出不兼容的信息 | 并列冲突内容、来源和日期，暂停确定结论 |
| 信息已经过期 | 信息的有效期、适用周期已结束，或存在更新信息使其不能代表当前状态 | 仅作历史背景，明示过期原因，不得支撑当前结论 |
| 来源不明隔离待核实 | 无法确认原始发布者、获取途径或可追溯链 | 与可用证据分开保存，不得参与确定结论 |

不得使用“基本可靠”、“已验证”或“有线索”等混合标签取代上述状态。同一结论同时出现“过期”或“冲突”特征时，拆分记录相应证据，不得将多个状态拼成新标签。

`evidence_state` 必须逐字使用上表七个受控值之一。任务方指令、管理层要求、研究截止时间、业务员或任务方预先设定的授权来源范围与访问范围、搜索范围和研究方法属于 `research_plan` 的任务控制，不是客户事实。输出时将它们放在独立的“研究计划/任务控制”部分；任何名为证据、客户事实、公司发现或缺口的表格/列表都不得包含这类任务控制行。不得为任务控制填写“不适用”等占位证据状态；如果记录结构含 `evidence_state`，就从该记录结构中完全移除任务控制。

未核验发件人身份或邮件头的入站邮件不得标为官方直接证据；无论证据状态如何，回复硬停和邮件助手移交始终优先。仅有粘贴文本、显示名或不完整转录时，保存当前文本或本地引用、客户主张、来源、观察日期、缺失的发件地址／邮件头／认证／主体关系，并使用与可追溯程度相符的受控状态；不得据此确认发件主体、职责或公司身份。身份缺口影响证据强度，但不得成为延迟停止开发触达或准备有边界 `email_assistant_handoff` 的理由。

实际尝试访问具体页面、数据库或附件后观察到无法访问，属于 `source_access_gap`，不是预设任务控制，也不是客户事实。必须单独记录来源名称或 URL、本次尝试日期、实际访问限制和受影响结论；不得写成“已检查”或“未发现”，也不得为没有读取到的内容编造 `evidence_state`。没有读取到证据时，直接写“无可登记证据”，不得创建带 `—`、“不适用”或其他占位值的证据行；证据表中每个非空数据行的 `evidence_state` 必须是七个受控值之一。需要解释真实证据的状态时，将解释放入独立的使用边界或备注字段，不得在受控值后追加括号、前后缀或组合标签。`批准本地产品事实` 应写入 `approved_product_reference` 或独立备注；若同时建立证据记录，`evidence_state` 只能原样填写 `官方直接证据`，不得写成 `官方直接证据（批准本地产品事实）`。

## 证据字段

每条关键结论必须保存一条独立、可追溯的证据记录，不得只在总结中笼统注明“已查官网”。

| 必填字段 | 记录要求 |
|---|---|
| 原文或本地证据引用 | 保存支持结论的最小必要原文，或批准本地资料的文件与位置引用 |
| 中文摘要 | 准确概括与结论相关的信息，不添加原文未包含的判断 |
| 来源类型 | 例如公司官网、政府登记、官方社媒、零售、评论、海关或行业来源 |
| 发布主体 | 记录页面、文件或数据的责任发布者；无法识别时明示为未知 |
| 链接或本地路径 | 保存可追溯的 URL，或已批准本地资料路径 |
| 发布日期 | 记录源内可见发布或更新日期；不可得时填“未知”，不得用查询日期倒填 |
| 查询日期 | 记录实际访问日期 |
| 语言 | 记录原文语言 |
| 地区 | 记录来源或内容适用的国家、市场或管辖区；无法判定时填“未知” |
| 访问范围 | 记录公开、本次已授权登录/付费、未授权或不可访问 |
| 证据状态 | 从本文“证据状态”的七个值中选择一个 |

## 来源能力边界

不同来源只能支持其可观察范围内的结论：

- 社媒热度只能表明平台内的可见互动，不等于销量、订单或市场份额。
- 用户评论可作为使用体验或重复主题的线索，不等于已证实的质量事实、故障原因或总体口碑。
- 第三方店铺可表明某个销售渠道的可见上架，不自动证明目标公司是制造商、品牌所有者或授权销售方。
- 海关数据只表明数据源覆盖范围内的可见贸易活动，不等于公司总体规模、全部贸易或采购预算。
- 客户自述、客户标识的第三方资料或转载内容属于客户主张，不自动成为本方公司事实或已批准产品事实。

## 公司资料可靠性

`reliability_summary` 只能使用下列一个结论：

| 可靠性结论 | 可观察条件 |
|---|---|
| 资料充分且一致 | 关键结论有直接或相互印证的证据，主体已解析，无影响主要判断的冲突或缺口 |
| 整体可信但存在缺口 | 主要判断有证据支持，但仍存在已列明、不致使主要判断失效的缺口 |
| 存在重大冲突需要核验 | 主体、关系、关键活动或其他主要结论存在尚未解决的材料冲突 |
| 证据不足无法判断 | 可追溯材料不足以支撑主要判断，或核心信息不可访问 |

公司资料可靠性只评估资料对公司研究结论的支撑程度，不代表客户价值、优先级、信用、付款能力或是否应触达。

`reliability_summary` 必须只给出上表中的一个受控结论，并紧随三个独立区块：支持证据、反对或冲突证据、剩余缺口。每项引用相应证据编号或来源访问缺口；没有反对证据时写明“在已查范围内未见反对或冲突证据”并保留覆盖边界，不得省略该区块，也不得用数字评分替代受控结论。

输入只说明某个字段“完整”“已填写”或“存在”时，只能确认该字段的结构状态；不得把它解释为字段中的待验证问题已经解决、剩余缺口已经消失或可靠性结论已经成立。字段原文不可读取时记录 `当前上下文不可读取`，另行保留待核验缺口。

## 联系人候选顺序

`contact_candidates` 的排序目标是找到与当前业务主题最匹配且可合规使用的职业联系路径，不得只按职位高低排序。

每个候选人必须分别记录并比较：

1. 职责匹配：公开职责与已确认业务主题的相关度。
2. 公开活跃：近期是否有可验证的公开职业活动。
3. 渠道可得：是否存在可访问的公司或职业渠道。
4. 真实性：姓名、职位、雇主关系和联系信息是否已核实。
5. 来源可靠性：联系信息的原始来源是否可追溯、当前且与本人对应。
6. 使用权限：联系信息属于正常使用、限制使用还是隔离待核实。

当至少找到一名使用权限为“正常使用”的候选人时，输出一名主要联系人候选、候补顺序及每个顺位的依据。

当已完成适用的必查渠道检查，但没有找到使用权限为“正常使用”的候选人时，主要联系人结果必须原样输出 `未找到可正常使用的主要联系人`，并记录联系人缺口和已检查渠道。不得猜测或编造姓名、职位、雇主关系或联系信息来填补空缺。

没有使用权限为“正常使用”的联系人时，未取得业务员对该具体联系方式的逐项批准前，禁止准备或执行联系；已逐项批准的“限制使用”或“隔离待核实”条目可作为“已批准受限例外”进入候选联系顺序和联系材料。原有联系信息来源、真实性、来源可靠性和使用权限必须保持不变，且不得冒充“正常使用”。

联系人输出是内部候选建议；最终选择、联系内容、渠道、时机和是否发送均由业务员决定。

## 联系信息权限

联系信息的真实性、来源可靠性和使用权限是三个独立维度，不得用其中一个推定另一个。每个联系方式必须保留以下独立字段：

| 字段 | 允许值与要求 |
|---|---|
| 联系信息来源 | 具体链接或本地来源引用；无法追溯时标记“来源不明” |
| 真实性 | 已核实 / 待核实 / 无法核实，并记录核实依据 |
| 来源可靠性 | 可追溯且直接 / 可追溯但间接 / 来源不明，不得用“联系方式看起来有效”代替 |
| 使用权限 | 正常使用 / 限制使用 / 隔离待核实 |

使用权限按可观察条件判定：

- 公司官网、官方职业主页或本人公开声明用于职业联络的信息，标记为“正常使用”。
- 私人手机、私人邮箱或其他未公开声明用于职业联络的个人方式，标记为“限制使用”。
- 原始来源、获取途径或用途无法确认的联系信息，标记为“隔离待核实”。

同一条信息同时符合“私人方式”和“来源或用途无法确认”时，使用更严格的“隔离待核实”，不得降为“限制使用”。业务员逐项批准只新增批准状态；不得把“隔离待核实”改成“限制使用”或“正常使用”。

“限制使用”或“隔离待核实”的信息不得进入任何联系材料，不得被用于准备、建议或执行联系；只有在业务员对该条具体信息给出明确批准后，才能进入联系材料。批准不会将其真实性或来源可靠性自动改为已核实。

`contact_candidates`、联系人缺口和逐项审批包中的每一种联系方式都必须单独成条，并逐项显示以下四个独立字段：`联系信息来源`、`真实性`、`来源可靠性`、`使用权限`。不得用一段综合叙述、通用证据状态或其中一个维度替代其他维度。无法追溯来源且无法核实用途时，使用这一明确组合：`联系信息来源 = 来源不明`、`真实性 = 待核实`或`无法核实`、`来源可靠性 = 来源不明`、`使用权限 = 隔离待核实`；“待核实”不能单独作为来源可靠性或使用权限的值。业务员批准某一具体条目后，在该条目旁另记批准状态；原有真实性、来源可靠性和使用权限标签必须全部保留，批准不改写这些标签。

## 风险硬门

当出现任一可观察条件——疑似制裁命中、重大诉讼、目标与记录主体冲突、明显经营异常、重大或反复的付款异常、实质性信用异常、交易身份异常，或与目标主体匹配的重大监管处罚或严重监管异常——必须将 `risk_gate_status` 设为 `暂停待业务员审核`，并暂停正常推荐。交易身份异常包括买方、合同方、付款方、收款受益人或要求联系主体之间的关系无法证实。

普通监管公告、常规登记变化或尚未显示重大性的监管记录只作为研究证据，不自动触发风险硬门；先记录发布主体、管辖区、日期、主体匹配和实际内容。硬门动作表示“需要业务员审核并暂停”，不等于已经作出违法、失信、信用不足或拒绝交易的结论。

风险硬门命中后，输出必须包含：

- 命中内容及其类型。
- 原始来源、发布主体、名单或记录版本、发布日期与查询日期。
- 目标主体与命中主体在法定名、别名、地址、主体编号、董事或受益所有人等方面的匹配结果。
- 同名或近似名风险，以及尚不能排除的主体。
- 来源冲突、不可访问来源、缺失主体识别信息和其他缺口。
- 可执行的下一步核验，以及需要业务员确认的事项。

在业务员明确确认是否继续前，不得将风险结果表述为“已通过”或“已排除”，不得恢复正常推荐、准备联系材料或指导发送。业务员保留是否继续的最终决定权。

`risk_gate_status = 暂停待业务员审核` 时，风险硬门优先于有效事件：只记录事件证据、待办和既有 `regular_cadence_anchor` 历史值，不生成联系材料或渠道，也不计算或展示事件触达、常规触达的下一建议日期。业务员明确批准继续后，若事件仍相关，立即准备事件触达候选，且不得重置 `regular_cadence_anchor`。
